# 39. Dashboard 搜索防抖与竞态取消

## 本次任务做了什么
本次任务对 Dashboard 当前目录搜索做了一轮前端交互性能优化，补上了输入防抖和旧请求取消能力。

完成之后，用户在搜索框连续输入关键字时，不会每敲一个字都立刻打一次搜索请求；只有在短暂停顿后才会发起最新请求。如果上一轮搜索还没返回、用户又继续输入或直接清空搜索，旧请求会被主动取消，不再有机会用过期结果覆盖当前列表。

## 涉及的文件清单
- `web/src/api/dashboard.ts`
- `web/src/hooks/useDebouncedValue.ts`
- `web/src/lib/isRequestCanceled.ts`
- `web/src/features/dashboard/useDashboardHome.ts`
- `docs/plan.md`

## 核心设计决策和原因
- 防抖逻辑抽成独立 `useDebouncedValue`。
  这样 `useDashboardHome` 不需要继续堆叠定时器细节，后续如果其它输入场景也要做防抖，可以直接复用。
- 请求取消放在 Dashboard 搜索状态层处理，而不是塞到 axios 全局拦截器。
  搜索请求的取消是一个页面级交互策略，不适合污染全局请求行为；放在业务 Hook 中更容易理解“为什么取消”和“何时取消”。
- 搜索输入变化时先中止旧请求，再等待防抖后的新关键字发起新请求。
  这样既能减少无效请求数量，也能避免旧请求晚返回后把新关键字对应的结果顶掉。
- 取消请求不视为错误。
  主动取消属于正常控制流，不应该把 Dashboard 右侧列表切成“搜索失败”状态，也不应该干扰用户继续输入。

## 前端数据流说明
- `searchKeyword` 继续保存输入框中的实时值，`debouncedSearchKeyword` 负责承接真正参与搜索请求的稳定值。
- 业务 Hook 会维护当前激活中的 `AbortController`；当输入继续变化、目录切换或搜索被清空时，旧控制器会先执行取消。
- 列表渲染继续沿用现有搜索结果、排序切换和虚拟列表链路，不需要额外拆新的结果页或状态容器。

## 已知 TODO / 待改进项
- 当前防抖时间固定为 300ms，后续如果要做移动端或不同输入场景的细分体验，可以再抽成可配置项。
- 当前只做前端请求级 perf 优化，没有引入后端缓存、搜索统计或服务端限流策略。
