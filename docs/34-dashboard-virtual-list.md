# 34. Dashboard 文档列表虚拟列表

## 本次任务做了什么
本次任务聚焦首页右侧文档列表的性能优化，没有扩展新的业务接口，而是补上了需求里明确提到的虚拟列表亮点。

完成之后，Dashboard 会在文档数量超过 40 条时自动切换到手写虚拟列表，只渲染可视区附近的文档卡片；如果用户进入文档行内重命名，列表会临时回退到全量渲染，保证输入框聚焦和高度变化都保持稳定。

## 核心设计决策和原因
- 这次只处理右侧文档列表，不连带改左侧文件夹列表。
  右侧文档列表是当前最容易随着数据量增长而膨胀的区域，也更适合作为独立性能亮点先落地，避免一次把范围扩到两个列表。
- 继续用手写 Hook，而不是引入第三方虚拟列表库。
  当前需求只需要一个固定高度、滚动窗口式的列表，手写方案足够轻，也更方便后续手写重构和讲解实现思路。
- 文档行内重命名时回退全量渲染。
  行内编辑表单高度和普通文档卡片高度不同，还涉及输入框自动聚焦；与其强行支持动态高度，不如先用最稳的方式保住交互体验。
- 普通文档卡片高度收敛为固定下限。
  这样虚拟窗口计算只需要根据滚动位置和容器高度推导可见区间，不必额外做运行时测量。

## 前端组件结构和数据流说明
- `useVirtualListWindow` 负责监听滚动容器位置与高度，计算当前需要渲染的文档区间。
- `DocumentListPanel` 负责判断当前是“全量渲染”还是“虚拟渲染”，并根据结果计算顶部与底部占位。
- `DocumentListItem` 继续负责单条文档的展示、菜单与选中态，只额外收敛了普通展示态的最小高度。

## 已知 TODO / 待改进项
- 当前只覆盖右侧文档列表，如果后续左侧文件夹数量也明显增大，再单独评估是否需要补文件夹虚拟列表。
- 当前虚拟列表采用固定高度策略；如果以后文档列表出现多行摘要、标签等可变高度内容，需要重新讨论测量和滚动修正方案。
